## 說明

- 無論是設計 RESTful API、規劃資料表，或是以使用者的角度查看資料，我們常會面對同一個問題：該怎麼找到一個「唯一值」來識別每一筆資料，而且不依賴身分證字號、手機號碼、Email
  這類可能會變動、又涉及個資的欄位?
- 有了這樣的主鍵，API 或資料表只要一查，就能準確取得唯一的一筆資料。
- 以下簡單介紹一下目前常見的主鍵類型。

----

## 主鍵類型

### 流水號
----

- 流水號可說是最常見的主鍵作法。從 1 開始，每新增一筆資料就加 1，一般資料表整數欄位 (INT, 32-bit)最大約 21 億；部分資料表支援
  BIGINT, 64-bit) 則可到約 9.2 × 10¹⁸ (約 922 京)，實務上幾乎不可能用完。
- 但流水號有明顯的缺點，例如：
    - `/order/18`，流水號第18筆是自己的訂單資訊。但就是會好奇是否有第19筆? `/order/19`；'上一位比我早下單的人買了什麼
      `/order/17`
    - `/order/2000`，可能會洩漏訂單總數量
    - `/order/100, /order/102, /order/103`，有部分流水號可能會跳號，造成可用的流水號減少

### 通用唯一識別碼 (UUID/GUID)
----

- UUID 的英文全稱是 Universally Unique IDentifier；GUID 是微軟系統內的別稱 (Globally Unique Identifier)
  。雖然兩者名詞不同，但是基本上都在說同一件東西。
- 主要是透過產生 128 位元字串，只要字串夠長，學理上重複的機率會很低 (但不代表必定不會重複)。

#### UUID v4
----

- UUID v4 出現在 RFC-4122[^RFC-4122]，屬於"完全隨機"產生的UUID，很適合作為主鍵需求
    - `63cc0671-38c9-4fdc-b964-9c5b1502f72d` or `63cc067138c94fdcb9649c5b1502f72d`
        - 這個"-"也作為人在辨別時的輔助符號，在資料庫中基本上不會儲存"-"
- 但 UUID v4 在最作為資料庫主鍵時，因為隨機效果太好，導致資料庫使用的 B-tree 索引效果不佳造成索引碎片化問題，最後導致寫入效能下降。

#### UUID v7
----

- UUID v7 出現在 RFC-9562[^RFC-9562]，他屬於基於時間遞增下的"完全隨機"產生的UUID，很適合作為主鍵需求
    - `01a164d2-f48f-7a4e-baa5-28f84689b957`
- 他解決了 UUID v4 索引碎片化的問題，更適合作為資料庫主鍵。
- 但是也因時間遞增，所以會被推算出資料的建立時間與可能的先後順序

#### 前綴 ID (Prefixed ID)
----

- 前綴 ID不是什麼 RFC標準 或是 像流水號資料庫有內鍵功能的技術，而是業界的慣用作法。
- 他的目的是透過增加前綴`xxx_oooooooo`的作法，讓人可以快速辨別這是甚麼用途的主鍵，或它來自哪張資料表，例如:
    - `01a164db-8401-7908-ac9c-a7c463208f47` 與 `01a164db-8401-7e0d-9a65-7beb581a3905`
        - 你只知道這是兩個UUID v7，但無法得知這是哪張資料表來的主鍵。
    - `user_01a164d2f48f7a4ebaa528f84689b957`
        - Prefixed + UUID 7 變體，既知道這個主鍵可能來自 user 資料表，也保持 UUID v7 特性
- 對於 RESTful API 來說，也可以針對路徑制定驗證規則，例如 `/order/<odr_*>`:
    - 開發者或閱讀文件的人，能快速理解這個 ID 可以用在哪些 API。
    - 後端若收到前綴不符的 ID，可以立刻回傳錯誤。
- 實務上，建議前綴只在 API 層處理，資料庫仍儲存原本的 UUID:
    - **讀取時**：將 `<前綴>` 與 `<UUID>` 組合成 `<前綴>_<UUID>` 回傳。
    - **寫入/查詢時**：先用 `<前綴>` 驗證類型，再取出 `<UUID>` 進行後續的商業邏輯。

## 小結
----

- 目前並沒有「使用A方法作為主鍵」就是最好的方法。
- 要使用什模做法作為主鍵，全憑自身需求、情境來決定。
